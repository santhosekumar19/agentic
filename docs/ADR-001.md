# ADR-001 — Separate policy decision service from application orchestration

**Status:** Accepted for educational portfolio baseline (2026-11-14).

## Context

An enterprise assistant handles tenant-specific information and user-specific operations. Business authorization rules change independently from retrieval and frontend presentation. A trustworthy system needs traceable decisions and a single explicit deny outcome for unknown operations.

## Decision

The Node.js gateway resolves demo identity and calls a Java/Spring Boot policy endpoint before invoking Python retrieval. The gateway fails closed if the configured policy endpoint returns a denial, an error or is unavailable. Tenant ID used for retrieval comes from gateway-derived identity, never the browser's JSON body.

## Alternatives considered

1. Check role strings directly inside every route (simplest, higher policy drift).
2. Embed a shared library inside Node/Python (fast, but cross-language governance costs).
3. Use an external policy engine like OPA (best future scalability, more deployment complexity).

## Consequences

- **Benefit:** Independent testability, compliance demonstration, clearer policy ownership, and cross-language experience.
- **Cost:** Extra network dependency, deployment, schema governance, and latency.
- **Explicit limitation:** Demo identity headers are not authentication and must never be trusted outside localhost.

## Follow-up decisions

Introduce OIDC, versioned policy contracts, an external policy engine when needed, and contract tests across service boundaries.
